# AI 协作说明

> 评审维度第一条明确写着「开发过程真实透明、代码非拼接」。
> 这一页就是回答它：**哪些是 AI 写的，人做了什么判断，怎么验证。**

## 一句话

本项目由一名零编程基础的学生（作者本人）在 AI 辅助下完成。
**AI 承担编码，作者承担判断。** 判断的部分写在这里，因为那才是这个作品属于作者的部分。

## 分工

| 环节 | 谁做 | 说明 |
|---|---|---|
| 需求与取舍 | 作者 | 做什么、不做什么，全部由作者决定 |
| 架构选型 | 作者拍板 | Python + Streamlit + SQLite，理由是零基础环境下能在期限内跑通、评委能一键复现 |
| 代码编写 | AI | 绝大多数代码由 AI 生成，经作者运行验证 |
| 代码审查 | 作者 | 每个功能跑一遍、点一遍；不接受"看起来对" |
| 术语与话术 | 作者 | 界面文案、文档措辞由作者逐句改，AI 初稿普遍偏"公司腔" |
| 真实反馈来源 | 作者 | 指导教师对系统的现场反馈（见下），是 P13 那次大改的直接原因 |
| 测试 | AI 编写，作者定断言 | 断言什么由作者定（"导师答案必须盖过 AI 草稿"），代码由 AI 写 |

## 三次由人的判断推翻 AI 方案

这三件事比"我们的代码有多好"更能说明协作是真实的。

### 一、AI 建议做「六维评分」，作者否掉了

AI 给出的第一版方案是"结构 / 方法 / 数据 / 论证 / 规范 / 创新"六维打分——功能更唬人，演示更好看。

作者否掉的理由：分数不可验证，学生会为分数辩护而不是为内容改进；
而且这套评分与维普类系统正面重叠，我们没有数据优势。

**结果**：改成"只报要点覆盖，不打分"，并让答题前不显示考察要点。

### 二、初始定位撞进维普主场，作者重做了整个选题

最初的定位是"学位论文预评审平台"——查漏、评分、押题。
作者判断：这条赛道上维普有采购渠道和比对库，硬碰没有胜算。

**结果**：转向"导学协同"，把"答疑史"当成核心数据资产。
定位从"更好的检测工具"变成"别人做不了的事"。

### 三、导师现场反馈，推翻了一条写在文档里的判断

技术文档原本写着："刻意不做用户体系，等真要多角色登录了再拆。"

导师看完系统的当场反馈：**学生和指导老师没有绑定、老师那边看不到论文题目、
公开与隐私没有边界、提问没有分类。**

作者判断：这四条不是"技术复杂度"，是**数据模型缺了东西**。
补关系的成本，远小于让整个场景不成立。

**结果**：`qa` 表加四列、新增 `students` / `teachers` 表、新增老师端页面、
补可见性规则，并把原判断连同推翻依据一起写进技术文档（不删旧结论）。

## AI 做不了、也不该做的四件事

| 不做 | 原因 |
|---|---|
| 不生成答辩参考答案 | 答辩没有标准答案；模型一给，学生就背 |
| 不给论文打分 | 分数不可验证，会诱导学生为分数辩护 |
| 不裁决学术判断 | 涉及研究设计、数据可得性的结论必须由导师确认，Prompt 里强制输出这句话 |
| 不做语义判定的最终结论 | 规则能判的（引用、结构、要点）全部用纯函数，可复现、出错可定位 |

这四条的共同依据：**判断能不能交给 AI，取决于答错的代价谁承担。**

## 怎么验证这本说明没在吹

三条可查的：

1. `git log --oneline` —— 提交是否按功能递进，而不是一次全量导入
2. `docs/技术文档.md` 第 2.3.1 节 —— 被推翻的判断是否真的保留着原话
3. `pytest -q` —— 85 条测试是否真的全绿

**如果这三条查不出问题，说明过程是真的。** 反过来也成立：一次全量提交、
看不出迭代痕迹的仓库，功能做得再多也解释不了它是怎么来的。
